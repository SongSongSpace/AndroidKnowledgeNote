# 采集端无声、接收端刺耳音频：待验证的排障路径

核对日期：2026-11-25。状态：**现象描述待现场证据确认；根因未定位**。

## 已记录的现象与证据边界

原笔记记录了“采集端没有系统内部声音，也没有外部麦克风声音；接收端浏览器仍可能听到刺耳音频”。原文没有设备型号、系统与 WebRTC 版本、采集源、复现步骤、音频样本、PCM 波形、处理配置或时间对齐的日志。因此这是一条**待确认的现象描述**，不能据此断定 AGC、底噪或削波是实际根因，也不能把下文当作已验证的项目复盘。

“没有声音”至少要区分：环境中无人说话、输入设备输出近似静音、采集 PCM 全零、音频轨道静音或结束、没有发送音频轨道，以及仅在接收端听不到。它们位于不同环节，不能互相推导。

## 可以成立的机制与尚未证实的解释

WebRTC 的 Audio Processing Module（APM）可包含回声消除、噪声抑制和自动增益控制；具体是否启用、在哪一端启用，取决于实际采集管线和配置。[WebRTC APM 文档](https://webrtc.googlesource.com/src/+/9be6d6a88e8ae4bc91dd101dc4e1d473ae396dc1/modules/audio_processing/g3doc/audio_processing_module.md)

原笔记提出的**候选解释**是：输入并非全零，而有底噪；某一级增益把底噪放大，或后续处理造成失真，接收端因而听到刺耳声音。这需要采集前、处理后和接收端的对照样本，以及增益配置或实际值才能验证。WebRTC 的 GainController2 实现会考虑语音概率、噪声水平和削波余量，不能仅凭“静音”就断言它会持续抬高增益。[WebRTC GainController2 实现](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_processing/gain_controller2.cc)

若某一测量点的 PCM 样本**确实全部为零**，仅对该样本做普通乘法增益不会生成底噪；但这只排除该测量点之前的非零输入被放大，不能排除后续混音、处理、传输恢复、解码或播放链路产生声音。原文中“纯数字静音就可忽略”“无轨道就一般不会刺耳”都不应作为整条链路的结论。

其他候选方向仍包括扬声器回采产生的声学反馈、系统麦克风增强、手动 `GainNode` 或 SDK 增益、采集源或声道配置错误、缓冲和编码解码异常、接收端播放增益等。原文提到的“采样率不匹配”“降噪/回声消除 artifacts”也只是待排查方向，目前没有证据排序。

原笔记还列出 `pre_gain`、模拟麦克风增益、`post_gain`、操作系统麦克风增强（举例 +20 dB/+30 dB）及系统内录/loopback 是否输出底噪。它们应作为**具体实现存在时**的检查点，不能默认每条管线都有这些控制项，也不能预设无播放的系统内录必然全零。

## 建议的定位顺序（尚未执行）

| 步骤 | 要记录什么 | 这一步能区分什么 |
|---|---|---|
| 固定复现环境 | 设备、系统和浏览器或 Native SDK 版本，麦克风/系统内录/loopback 来源，扬声器状态，复现步骤与时间 | 避免把不同采集管线混成同一问题 |
| 检查轨道和配置 | 发送端有无音频轨道、轨道状态、浏览器请求约束与实际 `getSettings()`、Native 端 APM 和音源配置 | 区分“没有采到”与“采到后处理异常” |
| 对齐三个测量点 | 能取得时，保存采集后、处理/编码前、接收解码后或播放前的短样本；比较 RMS、峰值、频谱和削波 | 判断异常最早出现在哪一段，不能只凭接收端听感推根因 |
| 单变量对照 | 分别调整 AGC、系统增强、手动增益、降噪、回声消除及播放音量，每次只改一项 | 只有异常随某项变化且样本对应时，才提高该假设可信度 |
| 排除声学回路 | 耳机或静音扬声器复测，比较本地与远端播放 | 区分回采啸叫与数字链路失真 |

浏览器采集可检查 `navigator.mediaDevices.getSupportedConstraints()`、轨道 `getConstraints()` 与 `getSettings()`。`autoGainControl: false` 是请求约束，不能把写入该值当成已关闭全部系统或 SDK 增益；实际设置仍须核对。浏览器可用 Web Audio 的 `AnalyserNode` 观察波形或频谱；它**不是 Android Native 采集端 API**，只观察接入该节点的信号位置。[W3C Media Capture and Streams](https://www.w3.org/TR/mediacapture-streams/)、[W3C Web Audio API](https://www.w3.org/TR/webaudio-1.1/)

## 处理建议的适用条件

- **只有确认某级增益导致异常后**，才考虑限制该级增益或关闭对应 AGC；改动后复测正常语音是否过小。浏览器约束不会自动控制 Android Native、操作系统或硬件的全部增益。
- **只有确认输入底噪且场景允许丢弃低电平信号后**，才评估噪声门或噪声抑制；阈值不当会切掉轻声语音。
- **只有确认削波位置后**，才选择前级降增益或合适的限幅处理；接收端降低音量只能改变听感，不能修复发送端已削波的样本。
- 若异常在发送端样本中不存在，应继续查传输、解码、混音和播放，避免在采集端盲调。

原笔记给出的浏览器约束示意为 `autoGainControl: false`、`noiseSuppression: true`、`echoCancellation: true`。这些是浏览器采集的请求值，并非已验证的修复组合；逐项检查支持情况、实际设置和音质副作用后才能采用。原建议的手动增益上限、限幅或动态压缩、噪声门、关闭系统增强，也都须先定位异常所在环节。
